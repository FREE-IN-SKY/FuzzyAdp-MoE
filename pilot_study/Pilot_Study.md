
# Pilot study (organized by the normal experimental procedure)

Compiled on 2026-10-30. This document describes the pilot study in "the most reasonable experimental order": first fix the protocol, the starting-point settings and the fixed settings, measure the noise baseline, check the structure and loss, then determine the training hyperparameters step by step, diagnose the router learning rate, calibrate the fixed baseline, confirm the comparison methods, and design the controller. All numbers come from actual runs. The actual process was carried out in chronological order, and settings and rules were changed along the way; the full work log is in `Pilot_Plan.md`, and the steps that were overturned or bypassed are collected in the Appendix of this document.

**Each stage states its actual run conditions in the same way.** Any experiment not run under "the settings fixed by the previous step" is marked **[to be rerun]**; its original results are in Appendix B, and the main-text conclusion will be filled in after the rerun. Stages not yet carried out are marked **[pending]**. Reruns follow the stage order of this document (see 12.4).

## 1. Experimental protocol

### 1.1 Data

- Dataset: RSCD road-surface images (27 classes), using the original date-split lists (train.csv / vali_20k.csv / test_50k.csv); the dates of training, validation and test do not overlap.
- Subsets (`datasets/subsets/`, generated by `make_subset.py`, checksums recorded in `manifest.json`):
  - Training: each class is sampled at 4% of its class count in the full dataset, 41,130 images per subset, 6 subsets in total (seeds 0 ~ 5);
  - Validation: max(0.5%, 100 images) per class, 5,810 images in total, shared by all runs;
  - Test: the full date-split test set, 59,793 images, used only in the final evaluation (`evaluate.py --final`).
- Class prior π: the class proportions of the training subset, shared by all runs.
- Seeds: the pilot study uses only seeds 0 ~ 2; the main experiments use seeds 3 ~ 5. Seed k uses `train_s{k}.csv` and uses k as the training random seed (scheme A). The seed therefore changes both the training subset and the initialization, and their effects cannot be separated.

### 1.2 Metrics and the validation set

- **Primary metric:** validation A_π at the best epoch (per-class recall weighted by the class prior π). Checkpoints are selected by validation A_π. The primary metric is the maximum over all epochs of training, so it is inherently biased upward and is more affected by chance fluctuations than an average; each stage therefore also reports the mean A_π over the last 10 epochs and checks whether the two rankings agree, and states it truthfully when they do not.
- **Supplementary metrics (not used for selection):** BA, Macro-F1, mean A_π over the last 10 epochs.
- **Routing metrics (not used for selection, with only one exclusion condition):**
  - Minimum weighted usage: the minimum share among experts of the number of times each expert is selected into the top-2, combined according to π. **Exclusion condition: the minimum within the last 10 epochs of any seed < 5%** (uniform is 20%; 5% is set by hand).
  - Minimum top-1 share: the minimum of each expert's share (π-weighted) as the first choice, used to detect experts that "only serve as the second expert".
  - Minimum w share: the minimum of each expert's share of the mixture weights.
  - Normalized mutual information I(C;E)/H(E): the association between classes and expert assignment, used as a proxy for specialization.
  - cos gap, w1: the cosine-score difference between the two selected experts, and the larger weight.
- **Two problems with the validation set and how they are handled:**
  - **Repeated use:** there is only one validation set; it is used to select checkpoints, structure, training hyperparameters and routing parameters, and the fuzzy controller also reads it every epoch during training. When multiple selections are made on the same data, the score of the selected configuration on that data is biased upward (Cawley & Talbot, JMLR 2010). Switching to seeds 3 ~ 5 in the main experiments only changes the training subset; the validation set stays the same one and does not become independent again as a result.
  - **fuzzy reads the validation set:** all methods use the validation set to select checkpoints, but only fuzzy adjusts itself during training based on the validation set. Therefore, for any comparison involving fuzzy, in either the pilot study or the main experiments, no conclusion is drawn from validation results; only test-set results are used. Stage 8 also does not use validation accuracy as the basis for judging the fuzzy trial run.
  - **Small size:** the validation set has 5,810 images; 11 classes have only 100 images each (the sampling floor), and the largest class has 413; the validation samples of dry_mud and water_gravel come from at most 3 dates. For a class with 100 images, 1 more error changes that class's recall by 1 percentage point, so single comparisons fluctuate easily; BA and Macro-F1 are equal-weight averages over classes and are most affected by small classes, while A_π is weighted by the prior π and is less affected.
  - **Handling:** (1) validation A_π is used only for selection and process monitoring, not as a generalization estimate; (2) verdicts that change a default value, fix a range or set a final value use 3-seed seed-paired comparisons with a tie threshold X; (3) the paper's performance conclusions use only test-set results after all settings are frozen (59,793 images, about 10 times the validation set, evaluated only once).
  - **Do not enlarge the validation set or add more validation sets (decided 2026-10-30):** the original validation pool has 290,227 images, so technically a larger validation set or several validation sets could be drawn. But multiple validation sets cannot remove the upward bias caused by repeated use (the selections in every stage are still made on a validation set); a larger validation set would reduce fluctuation and also make the accuracy trend read by fuzzy more stable, but changing the validation set would invalidate all pilot-study results (best epoch, per-epoch curves, X, controller input distribution), and the main experiments must use the same validation set as the pilot study. Therefore the existing validation set is kept, and its effect is recorded as a limitation. The noise in the fuzzy accuracy trend is handled in Stage 8 through controller design (such as a larger trend window).

### 1.3 Starting-point settings, tie threshold X and selection rules

- **Starting-point settings (pre-declared defaults):** augmentation B, peak learning rate 1e-3, 70 epochs, weight decay 1e-4; λ0 = 1.5, σ0 = 0.2, τ0 = 0.5 (for the source, see Stage 1). The candidates of each stage are centered on the starting-point settings, and on a tie the starting-point setting is kept. Stage 4.3 changed the epochs from 70 to 50, and Stage 6 changed σ0 from 0.2 to 0.4; these are the two values changed so far. Stages 2, 3, 4.1, 4.2 and 4.3 are run under the starting-point settings; Stage 4.4 and Stages 5 ~ 8 are run at 50 epochs; the fixed baseline in Stage 6b and Stage 8 uses σ0 = 0.4. Each step depends only on the choices before it, not on the results of later stages.
- **X = 0.50 pp.** Defined as X = max(0.3 pp, range of the best A_π of Fixed MoE over 3 seeds under the starting-point settings); the measurement is in Stage 2. X is a decision rule, not a significance test; the floor of 0.3 pp is set by hand.
- **Origin of X (must be stated truthfully):** in the actual process, X was first measured as 0.43 pp under the initial settings (R0 router, with aux warmup), pre-registered, and used for the decisions of the early stages. When this document was compiled, it was replaced by 0.50 pp, remeasured under the starting-point settings (R4, no aux warmup). Checked item by item, all choices already made are the same under both thresholds (Appendix A.2). The paper and the response letter can no longer call 0.43 pp a pre-registered threshold used throughout; this replacement must be stated.
- **Single-seed comparison:** a difference from the highest value smaller than X counts as a tie, and on a tie the default is kept (in the epoch stage, the shortest is chosen). When the monolithic model and Fixed MoE disagree in their choice, Fixed MoE prevails.
- **When a single-seed result calls for departing from the default, confirm before changing:** additionally run seeds 1, 2 of that candidate, pair them with the default by seed, and change the choice only if the mean of d_k ≥ +X; otherwise keep the default. The exception is choosing the shorter epoch count on a tie: likewise additionally run seeds 1, 2 and pair them with the starting-point value; the criterion is mean of d_k ≥ −X (non-inferior). Reason: the observed single-seed differences fluctuate by about 1 pp (Stage 6), which is larger than X.
- **Multi-seed comparison:** compute seed-paired d_k = A_candidate,k − A_reference,k (k = 0, 1, 2).
  - Better: mean of d_k ≥ +X;
  - Non-inferior (acceptable): mean of d_k ≥ −X.
- **Statistical power:** the standard deviations of the existing paired differences are 0.25 ~ 0.72 pp, and the standard errors of the 3-seed mean are 0.14 ~ 0.42 pp, of the same order as X. Therefore "tie" and "non-inferior" only mean "no difference found at this precision", not that equivalence has been proven.
- **Rules written first:** the candidates and rules of each stage are written down before that stage runs, and rules are not changed after seeing results. Revisions and exceptions that actually occurred are in Appendix A.

### 1.4 Environment and reproducibility

- All training runs on one dedicated experiment machine (NVIDIA GeForce RTX 4070 Laptop GPU, driver 595.91.07; Python 3.12.12, torch 2.10.0+cu128, torchvision 0.25.0, timm 1.0.22, numpy 2.2.6, CUDA 12.8, cuDNN 91002).
- `runs/env_lock.json` records the reference environment; the training and evaluation scripts check versions before starting and refuse to run on a mismatch; every run writes the environment and the code commit hash into `config.json`.
- Training enables deterministic mode, and runs with the same configuration are bit-for-bit reproducible. Evidence on the experiment machine: the rerun of seed 0 under the initial configuration (R0, with aux warmup) is bit-for-bit identical to the original run in all numeric columns over the 70 epochs, in the evaluation metrics and in the per-image predictions; the reruns of seeds 1, 2 are likewise bit-for-bit identical (Appendix E).
- **Across code versions:** the runs used in this document span several code versions (Appendix E). Across two code changes (adding the R4 router; rewriting the auxfree path), the training numbers of fixed mode R0 and R4 are bit-for-bit unchanged; this was verified **on the analysis laptop** with short training (real data, 2 epochs, 20 steps per epoch), not on the experiment machine. Direct evidence on the experiment machine only goes up to after R4 was added (the reproduction of seeds 1, 2); after the auxfree rewrite, it was not re-verified on the experiment machine.
- Training diagnostics (`diag_*` fields, `val_routing.npz`) do not change training numbers (verified bit-for-bit identical with them switched on and off); they are used only for interpretation, not for selection.
- **Time cost:** the time cost of pilot-study runs is only recorded. Times of runs from different periods cannot be compared directly (a difference of about 30% was once observed for the same configuration; the cause was not found). Times in the paper come only from separate timing runs in the main-experiment stage (diagnostics off, interleaved by seed).

## 3. Stage 1: provisional routing defaults (λ0, σ0)

**Purpose:** Stages 2 ~ 5 need values for λ0 and σ0, but their formal calibration (Stage 6) must come after the training hyperparameters are fixed. This stage gives provisional values under which routing assignment is not imbalanced.

**Actual run conditions:** only one round of 20-epoch calibration was done, under the R0 router with aux warmup (Appendix B.1), which does not match the structure of the starting-point settings. It selected λ0 = 1.5, σ0 = 0.2; τ0 = 0.5 is taken from the initial value of Tutel `CosineTopKGate`.

**Rerun needed: no.** This stage only provides provisional values; Stage 6 recalibrates under the final settings, with the result λ0 = 1.5, σ0 = 0.4, τ0 = 0.5. σ0 differs from the provisional value, so, as originally required by this section, Stages 2 ~ 5 are rechecked (Stage 6b).

**Limitations:** the structure and training length of the calibration differ from the final settings; the selected λ0 and σ0 are both on the upper edge of the candidate grid at the time; the selection criterion was normalized mutual information, and the gap between first and second place is within seed fluctuation.

## 5. Stage 3: structure and loss checks

The choice of structure and loss affects all later stages, so it is checked under the starting-point settings before the training hyperparameters are tuned.

### 5.1 Stage 3a: removing the aux loss warmup

**Purpose:** the original design (γ_w(t) in Eq. (9) of the submitted paper) multiplies the auxiliary-loss coefficient by 0.1 for the first T_w epochs. This practice has no literature basis, leaves the controller with almost no control over λ during the first 1/3 of training, and does not put it under the same conditions as auxfree (which has no such coefficient). This checks whether removing it costs accuracy.

**Setup:** R4, starting-point settings, seeds 0/1/2; with warmup (×0.1 for the first 23 epochs) and without warmup, seed-paired.

**Rule:** d_k = A_without,k − A_with,k; adopt no warmup if the mean of d_k ≥ −X and no seed is excluded.

**Actual run conditions:** the with-warmup side is the 3 R4 runs in `runs/router/`, and the no-warmup side is the 3 runs of Stage 2. This check itself is a comparison of exactly these two conditions, so they can be used directly.

| Seed | With warmup | No warmup | d_k |
| --- | --- | --- | --- |
| 0 | 0.6987 | 0.6993 | +0.06 pp |
| 1 | 0.7017 | 0.7043 | +0.27 pp |
| 2 | 0.7030 | 0.7008 | −0.22 pp |
| Mean | 0.7011 | 0.7015 | **+0.03 pp** |

| | Early (epochs 4 ~ 23) median of the weakest expert's top-1 share | Early median of minimum weighted usage | Training aux loss (epochs 1 ~ 10) | Normalized mutual information (mean) |
| --- | --- | --- | --- | --- |
| With warmup | 10.4 / 8.3 / 14.2% | 16.7 / 16.7 / 16.3% | 1.01 ~ 1.03 | 0.218 |
| No warmup | 6.5 / 10.0 / 10.6% | 17.4 / 15.7 / 16.4% | 1.003 ~ 1.004 | 0.219 |

**Conclusion: adopt no aux warmup.** Mean d_k +0.03 pp, no seed excluded.

**Findings:**
- Full λ makes the assignment counts close to balanced from epoch 1 (aux loss close to its minimum of 1.0), but the early top-1 share of the weakest expert does not improve.
- Reason: f_i in L_aux counts the total selections in both top-2 positions; as long as an expert is often second, its f_i is normal, and the loss does not distinguish first from second place. This is a property shared by top-k balance losses of this kind. The balance score B likewise only looks at assignment counts.
- Therefore the reasons for removing warmup are: accuracy ties; no literature basis; same conditions as auxfree; the controller has full control over λ from epoch 4. It is not "a larger λ is needed early to prevent imbalance".

**Impact on the paper:** Eq. (9) of the submitted paper contains γ_w(t); the revision removes it, and Eq. (9) becomes L = L_cls + λ · L_aux. The statement "early training benefits from stronger load-balancing regularization" in Section III-E of the submitted version points in the opposite direction to the effect of γ_w(t); after the removal the two are consistent.

### 5.2 Stage 3b: router (R4 vs R0)

**Purpose:** confirm that replacing the original router (R0: two 3×3 convolution layers + BN + ReLU + Dropout + cosine head, 371,552 parameters) with the mainstream cosine router R4 (3,168 parameters, about 1/117 of R0) does not reduce accuracy. The reasons for switching to R4 are that its structure has a literature source and its compute is negligible (R0 costs 18.06M MACs per sample).

**Setup:** no aux warmup (the conclusion of Stage 3a), starting-point settings, seeds 0/1/2. R4 reuses the 3 runs of Stage 2.

**Rule:** seed-paired d_k = A_R4,k − A_R0,k; confirm R4 if the mean of d_k ≥ −X; if it is below −X, do not automatically fall back to R0, but stop and discuss (first check the routing diagnostics to judge whether the routing parameters are unsuitable for R4). If R4 is not adopted, the later stages must be redesigned.

**Actual run conditions:** R4 is the 3 runs of Stage 2 (`runs/stage6c/`, code `58c4a45`); R0 is 3 reruns without aux warmup (`runs/stage6c/moe-fixed_R0_lam1.5_sig0.2_aw0_*`, code `6ade43c`, no uncommitted changes); all ran to completion and were evaluated, with no errors in the logs and no NaN. Result file `runs/stage6c/study3b.json`, recomputed on the analysis laptop with matching results. The original comparison (both sides with aux warmup) is in Appendix B.4.

**Conclusion: R4 confirmed.** Mean d_k +0.31 pp, not below −X (−0.50 pp); no seed excluded on either side.

**Supplementary metrics (3-seed mean, not used for selection):** BA R4 0.5412 / R0 0.5389; Macro-F1 0.5413 / 0.5377; mean A_π over the last 10 epochs 0.6965 / 0.6941. The direction is consistent with the primary metric.

**Findings:**
- In all 3 seeds of R0, one expert is almost never the first choice (0.0% for seed 2 in the last 10 epochs), but its assignment count is normal (minimum weighted usage about 16%), and the exclusion condition is not triggered. - Time cost only recorded: R0 steady-state training takes about 85 ~ 95 seconds per epoch, R4 about 78 seconds (runs from different periods, not directly comparable, see 1.4).

**Limitations:** this only shows that "under the starting-point settings R4 is not worse than R0 by more than X"; it is not a comparison of the two structures each fully tuned.

**Purpose:** determine, in order, augmentation, peak learning rate, number of epochs and weight decay. Each step is run under the choice of the previous step.

**Setup:** Fixed MoE with R4, no aux warmup, λ0 1.5, σ0 0.2, τ0 0.5; the monolithic model is run alongside (the epoch step runs only MoE). Seed 0. ## 7. Stage 5: router learning-rate diagnosis

**Purpose:** the router shares the same learning rate as the backbone and the experts (common practice). The router is trained from scratch, and most of its parameters are insensitive to overall scaling, so the same nominal learning rate does not mean the same effective update size. Before calibrating the routing parameters (Stage 6), training diagnostics are used to check whether a separate learning rate is needed.

**What is checked:** the ratio of per-step relative updates across parameter groups; the router_emb norm and per-step angle change; output contribution (w share) vs assignment counts; GradScaler skipped steps; fluctuation of routing assignment on the validation set; the formation of the class × expert assignment matrix. There is no literature threshold for "abnormal"; this check is an exploratory judgment made after looking at the data.

**Actual run conditions:** the original analysis used runs with R0 + aux warmup (conclusion: no anomaly, share the learning rate; Appendix B.5). **The 3 50-epoch runs of Stage 4.3 carry all diagnostics, so no new runs are needed; they are reanalyzed before Stage 6, and the result is rechecked with seed 0 of the 6 candidates after Stage 6 is done.** If an anomaly is found, stop and discuss; the content after Stage 6 may have to be redone.

**Results (2026-10-31, reanalyzed on the analysis laptop; data: the 50-epoch, wd 1e-4 seeds 0/1/2 of Stage 4.3, and the wd 0.01 / 0.05 / 0.1 seed 0 of 4.4): no anomaly seen; keep sharing the learning rate.**

1. **Effective step size** (ratio of `diag_step_update_*_mean` to experts, wd 1e-4, 3 seeds): at epoch 1, router_emb is 15 ~ 18 times and router_proj 3.9 ~ 4.3 times; from epoch 10 to the end, router_emb is 1.7 ~ 3.1 times, router_proj 1.7 ~ 2.6 times and shared 0.84 ~ 0.97 times, with none approaching 0 late in training. The large early router_emb step is consistent with its small initial norm (0.08 ~ 0.10): the norm is about 0.45 ~ 0.50 at epoch 10 and 0.84 ~ 0.95 at the end.
2. **Per-step angle change of router_emb:** mean 0.39° ~ 0.44° at epoch 2, 0.11° ~ 0.12° at epoch 17, 0.006° ~ 0.007° at the end; maximum 1.1° ~ 1.3° (epochs 2 ~ 3).
3. **Output contribution vs assignment counts:** over the last 10 epochs the difference between each expert's w share and weighted usage is within 4.2 pp; minimum w share 13.7% ~ 16.1%.
4. **GradScaler skips:** 13 ~ 16 steps over the whole run, 3 steps in epoch 1, then about 1 step every 3 ~ 4 epochs, consistent with the period of dynamic loss scaling; not an anomaly.
5. **Routing assignment fluctuation:** the fraction of top-1 assignments that change each epoch is 0.15 ~ 0.27 in epochs 2 ~ 15 and 0.03 in the last 10 epochs; its Spearman correlation with lr is 0.93 ~ 0.97 across the 6 runs; its correlation with 1/‖router_emb‖ is 0.94 ~ 0.98 under wd 1e-4 and drops to 0.86 / 0.56 / 0.12 under wd 0.01 / 0.05 / 0.1 (once the norm is pushed down by wd, the relation no longer holds). The fluctuation is determined by the learning rate, the same conclusion as Appendix B.5.
6. **Class division of labor:** the first epoch after which the distance between the top-1 assignment matrix and that of the last epoch stays below 0.10 is epoch 21 / 26 / 22 (wd 1e-4 seeds 0/1/2; epoch 31 / 21 / 22 for wd 0.01 / 0.05 / 0.1 seed 0), corresponding to an lr of about 3.5e-4 ~ 6.8e-4. An expert top-1 share below 5% appears only in the first 8 epochs (expert 1 of wd 1e-4 seed 0, in 6 epochs; none in seeds 1, 2), and all recover afterwards; there is no expert that "only serves as the second expert". The 3 seeds form different divisions of labor (for example, the standing-water classes go to one expert in seed 1 and to another in seed 2); normalized mutual information 0.206 ~ 0.242.

**Decision:** no anomaly; Stage 6 keeps sharing the learning rate. The basis is the same as Appendix B.5: the late-training ratio of router step size to experts is stable at about 2 times; the large early step comes from the small initial norm and is concentrated in the learning-rate warm-up period; assignment fluctuation is determined by lr, and there is no direct basis for X-MoE's modification of fixing the expert_emb norm; GradScaler skips are a normal mechanism. This is an exploratory judgment made after looking at the data. Recheck with seed 0 of the 6 candidates after Stage 6 is done.

**Recheck (2026-11-01, reanalyzed on the analysis laptop; data: seed 0 of the 6 candidates, plus seeds 1, 2 of σ 0.4):** the step-size ratios, angle changes and routing fluctuation are close to those of the center point; keep sharing the learning rate. For σ 0.4 seed 0, the weakest expert's top-1 share is below 5% in 33 epochs, the last time at epoch 44, with a minimum of 4.4% over the last 10 epochs; for τ 0.25 seed 0 it is 21 epochs, the last time at epoch 25. Therefore "below 5% appears only in the first 8 epochs" holds only at the center point. The exclusion condition only looks at usage and was not triggered. The cause was not found.

## 8. Stage 6: fixed baseline calibration (λ0, σ0, τ0) and acceptable ranges

**Purpose:** (1) fixed is the baseline in the main comparison and must be tuned under the final settings; (2) give the acceptable ranges of λ, σ, τ that cause no loss of accuracy, to be used as the variation ranges of schedule and fuzzy in Stage 8.

**Setup:** R4, no aux warmup, augmentation B, lr 1e-3, wd 1e-4, 50 epochs. Centered on (λ 1.5, σ 0.2, τ 0.5), one parameter is changed at a time: λ ∈ {0.5, 1.5, 4.5}, σ ∈ {0.1, 0.2, 0.4}, τ ∈ {0.25, 0.5, 1.0}. The center point is the 3 50-epoch runs of Stage 4.3.

**Reference:** V-MoE adds noise with standard deviation 1/E to the logits of a linear router (0.2 for E = 5), with aux coefficient 0.01; Tutel's initial τ is 0.5, and X-MoE's initial τ is 0.3 (both learnable). In this project the noise is added to the cosine scores and then divided by τ, so the scale differs; these are for reference only.

**Rules:**
1. Exclusion: minimum weighted usage < 5% within the last 10 epochs for any seed.
2. Each candidate runs 3 seeds, seed-paired with the center point.
3. **Final values:** a candidate value is adopted when its mean d_k ≥ +X; when two or more parameters are adopted, the combined configuration is additionally run with 3 seeds and the combination is adopted when its mean d_k ≥ +X, otherwise only the single change with the largest mean d_k is adopted; in all other cases the center point is kept.
4. **Acceptable range:** a value is acceptable when it is not excluded and its mean d_k ≥ −X; the [min, max] covered by the acceptable values of each parameter is used as its variation range in Stage 8.
5. The results of the additional runs are handled by the rules above no matter what they are, including the case where a parameter's acceptable range shrinks to only the center value (e.g. τ can only be 0.5); if that happens, the parameter is not adjusted in Stage 8, and this is stated in the paper.

**Purpose:** The rule base and membership functions of the submitted version (Table I) were designed for the old structure (LayerNorm router, τ 0.9) and were not checked after switching to the cosine router and R4: under the measured inputs τ mostly sits at the upper bound, σ is almost fixed at 0.12, and T_fast mainly reflects validation-set noise (Stage 6 "controller input distribution"). ### 10.1 Design basis (2026-11-03)

**Measured effect of the three outputs in this project (fixed runs of Stages 6 and 6b, 50 epochs, median over 3 seeds; open-loop data):**

| Configuration | B median (epochs 2 ~ 10 / 11 ~ 30 / 31 ~ 50) | Weakest expert top-1 share (early / late) | Final w1 | Final cos gap | Normalized mutual information | A_π relative to center |
| --- | --- | --- | --- | --- | --- | --- |
| λ 0.5 | 78.9 / 82.1 / 83.2 | 10.2 / 12.1% | 0.721 | 0.504 | 0.236 | +0.44 pp |
| λ 1.5 | 80.6 / 84.7 / 86.2 | 8.2 / 12.7% | 0.710 | 0.467 | 0.219 | 0 |
| λ 4.5 | 78.0 / 83.3 / 86.0 | 7.9 / 12.9% | 0.728 | 0.539 | 0.191 | −0.22 pp |
| σ 0.1 | 79.4 / 82.7 / 83.0 | 10.9 / 14.9% | 0.687 | 0.388 | 0.223 | +0.23 pp |
| σ 0.4 | 81.8 / 86.4 / 87.4 | 8.1 / 8.1% | 0.720 | 0.461 | 0.248 | +0.59 pp |
| σ 0.8 | 69.9 / 74.1 / 74.5 | 10.7 / 10.8% | 0.596 | 0.133 | 0.269 | +0.46 pp |
| τ 0.25 | 78.5 / 83.6 / 85.9 | 7.8 / 11.1% | 0.852 | 0.581 | 0.244 | +0.40 pp |
| τ 1.0 | 79.5 / 82.0 / 83.4 | 11.6 / 15.5% | 0.619 | 0.473 | 0.207 | −0.05 pp |

- **λ:** Within 0.5 ~ 4.5 it has almost no effect on B (minimum usage is above 14% in all cases); what it changes is the degree of specialization: the larger λ, the lower the normalized mutual information. In this setting balance is not maintained by a large λ; the cost of λ is a weaker division of labor.
- **σ:** Between 0.1 ~ 0.4 B rises slightly; at 0.8 B drops to 70 ~ 74, the weights of the two experts approach the average, and the per-epoch change in routing doubles. σ is exploration; its cost is that the division of labor and the weights get flattened.
- **τ:** Does not change the assignment, only the weights of the two experts (w1 0.852 vs 0.619); with small τ the weakest expert's top-1 share is lower. Neutral for accuracy.
- **Inputs:** Under acceptable configurations B is rarely below 75; real imbalance appeared only under the old calibration's λ 0.01 / 0.5 and under σ 0.8. T_fast is dominated by validation-set noise; the meaning of T_slow depends on the window.

**The three stages of training (per-epoch data of the fixed center point and σ 0.4):**

| Stage | Epoch | Learning rate | Fraction of routing top-1 changed per epoch | Training accuracy | Characteristics |
| --- | --- | --- | --- | --- | --- |
| Early | 4 ~ 10 | Near peak | 0.21 ~ 0.25 | < 0.90 | Assignment changes heavily, B fluctuates most (p5 73.5), weakest expert top-1 share is lowest |
| Middle | 11 ~ 30 | 9e-4 → 4e-4 | 0.12 ~ 0.19 | 0.90 → 0.99 | Division of labor forms; the class × expert matrix settles in epochs 21 ~ 26 (Stage 5) |
| Late | 31 ~ 50 | < 4e-4 → 0 | 0.025 ~ 0.09 | ≈ 0.999 | Assignment is essentially frozen; control parameters can only change the weights |

Routing changes are determined by the learning rate, not by the control parameters.

**Direction from the literature:** (1) A 2026 preprint (Three Phases of Expert Routing, arXiv 2604.04230) divides load balancing in MoE training into three stages, surge, stabilization and relaxation, and suggests reducing the balance-loss coefficient in the relaxation stage (not validated experimentally); (2) Skywork-MoE (arXiv 2406.06563) drives the balance-loss coefficient by the token drop rate, increasing it under imbalance and decreasing it under balance, smoothed by a moving average; it is the published approach closest to fuzzy; the same paper finds that when the gate is too flat the output is close to a simple average, and that sharpening the gate lowers the training loss (corresponding to reducing τ); (3) The evidence on noise exploration is mixed: tutorial-type sources suggest high noise early and low noise late; MirrorMoE (arXiv 2610.22353) finds in language-model pretraining that random routing throughout training is worse, but did not test adding noise only in the early stage; in this project σ 0.4 is better than 0.2, and 0.8 is a tie; (4) StableMoE (ACL 2022) freezes routing in the late stage; in this project late-stage routing is already frozen naturally by learning-rate decay. **One fact that must be stated honestly: within the acceptable range fixed never really became imbalanced; if fuzzy has an advantage, it comes from the trajectory of changing λ, σ, τ by stage, not from correcting imbalance.**

**Derived stage-wise control intent:**

| Stage | λ | σ | τ | Rationale |
| --- | --- | --- | --- | --- |
| Early (assignment not settled) | Medium to high | High | Unchanged | If imbalance happens it will only happen here; exploration costs least while the assignment is not settled; no sharpening before the division of labor forms |
| Middle (division of labor forming, B normal) | Medium to low | Medium | Slowly decreasing | Large λ suppresses the division of labor; start sharpening |
| Late (assignment frozen, B stable) | Low | Low | Low | Balance can no longer change, so λ is only a perturbation; noise only adds variance; sharpen the weights |
| B imbalanced in any stage | High | High | Increase (flatten weights) | Imbalance is handled first |

### 10.2 Design (written 2026-11-03; config file `p1/fuzzy_v2.json`, rules read from the JSON by the code)

**Framework:** The controller cannot see the epoch and can only infer the stage from the inputs. T_slow (window 10) serves as the stage indicator: in the early stage it is almost always positive ("rising"), in the late stage it shrinks to near 0 ("plateau"); T_fast (window 3) serves only as a "sharp drop" alarm, with its threshold placed outside the noise. The rule base fully covers all 9 combinations of B × T_slow, plus 1 alarm rule; conditions are joined only by "and", and the "or" in R1 of the submitted version is removed.

**Inputs (universe and membership functions based on the measured quantiles of fixed σ0 0.4, 50 epochs, three seeds):**

| | Condition | Δτ | λ | σ | Intent |
| --- | --- | --- | --- | --- | --- |

Correspondence with Table I of the submitted version: old R1 is split into new R1 / R2 / R10 (removing the "or"); old R2 / R4 correspond to new R5; old R3 to new R7; old R5 to new R4; old R6 to new R8; new R3, R6, R9 are added to complete the combinations.

**Four decisions on methodological positions (2026-11-03, adopted by the author at the suggested values):**
- **Direction of σ when accuracy drops (R6, R10):** take "medium" (baseline 0.4), neither increasing nor decreasing it. The submitted version argued for increasing σ to prevent collapse; the data only show that large σ flattens the weights and the division of labor, and cannot answer how σ should move during a drop. Exploration is left to the early stage.
- **Windows:** T_fast 3, T_slow 10 (suggestion of 2026-10-27, undecided at that time). Enlarging the window suppresses noise only to a limited extent (standard deviation 0.0098 → 0.0084); the real effect of changing the window is to make T_slow a stage indicator, and the levels are redefined accordingly. Cost: T_slow has no value before epoch 11; during this period only rules without T_slow (i.e. R10) are used, and when no rule is activated the value of the previous epoch (i.e. the baseline) is kept; in the code this is `early_mode`.
- **τ:** kept in the rules, decreased only under "perfect", with a smaller step. In the data τ is neutral for accuracy, but it determines how sharp the weights are and is part of the method.
- **Start and end points of schedule:** linear, λ 4.5 → 0.5, σ 0.8 → 0.1, τ 0.5 → 0.25, i.e. the nominal trajectory of the control intent in 10.1; the only remaining difference from fuzzy is "open-loop by epoch" vs "closed-loop by state". τ does not start from 1.0, because there is no basis for first flattening and then sharpening in the early stage. In the paper, "covers the same range" must be changed to "covers the same λ, σ range, with τ going from the same start point to the same end point".

**Code (`p1/train_moe.py`, 2026-11-03):** rules are read from JSON (each `{"if": {input: level}, "then": {output: level}}`, conditions joined by "and"), and the log columns for rule activation are generated from the rule names; an early subsystem for when T_slow has no value; `--fuzzy-config` defaults to `fuzzy_v2.json`, `legacy` is the submitted-version controller (only for reproducing old runs); the schedule start and end points are the new defaults. All modes read the window and β from this JSON to record the controller inputs, so from now on the T_slow recorded by fixed, schedule and auxfree runs is computed with window 10 (affects only the logs, not training). Verified on the analysis laptop with reduced data (128 validation images, 14 epochs, 2 steps per epoch): no inference failures, only the alarm rule acts in epochs 4 ~ 11, from epoch 12 the outputs match the activated rules, and schedule goes linearly to the end point. This verifies only the logic, not training quality.

### 10.4 Stage 9: robustness under poor starting points (decided 2026-11-03; done 2026-11-05)

**Purpose:** the current comparison is made at the calibrated baseline (λ0 1.5, σ0 0.4, τ0 0.5, selected from 18 runs in Stage 6), where fixed never became imbalanced, so the controller's corrective rules have no real events to correct. ### 11.3 Evaluation

- **checkpoint:** each run's `best.pth` (the epoch with the highest validation A_π), as in the pilot study, used for the verdict. The test results of `last.pth` (the 50th epoch) are reported as a supplement (D2) and are not part of the verdict: the best epoch is selected by the validation set, and fuzzy reads the validation set; `last.pth` involves no selection and is used to check whether the conclusions depend on checkpoint selection. This adds only evaluations, no training.
- **Test metrics:** A_π (primary metric), accuracy, BA, Macro-F1; for each method, report the mean and range over the 3 seeds (format of Table II in the paper). Per-class recall and confusion matrices are kept in each run's `test_eval_*/metrics.json` and not aggregated.
- **Routing metrics (descriptive only; decided by the author following the recommendation, 2026-11-06):** the paper's routing table uses the validation set, with the same definitions as the pilot study's `routing_report`: minimum weighted usage and minimum top-1 share take the minimum over the last 10 epochs (from the per-epoch records in `history.csv` and `val_routing.npz`); class-expert normalized mutual information and the maximum assignment similarity between two experts come from one evaluation of `last.pth` on the validation set (the assignment matrix in `val_eval_last/metrics.json`). The same four metrics for `best.pth` on the test set (single evaluation, no per-epoch version) are a supplement. **Definition of assignment similarity:** for each expert, the fraction of samples in each class for which it is selected into the top-2 forms a 27-dimensional vector; take the maximum of the pairwise Pearson correlations; if an expert's fractions are all identical (e.g., never selected), that pair is undefined and skipped. The algorithm for the submitted version's "expert-pair correlation" cannot be found in the old code, so the new values cannot be compared with the old values (0.56 / 0.38).

### 12.3 Main findings

1. Training is bit-for-bit reproducible; the diagnostics switch does not change training values.
2. Under the starting-point settings, Fixed MoE and the monolithic model (single seed) have similar accuracy, with no visible difference.
3. Removing aux loss warmup gives tied accuracy. The top-k balance loss constrains only assignment counts and cannot prevent "acting only as the second expert"; the balance score B also cannot see it. Under the starting-point settings this problem is not severe (top-1 share of the weakest expert 12.4% ~ 17.4%); it is only monitored and reported, not fixed.
4. Fluctuations in single-seed comparisons can reach about 1 pp, exceeding the range over 3 seeds; changing defaults and determining ranges require multiple seeds.
5. The faithful auxfree has no collapse with 5 experts and image-level top-2 routing at both 70 epochs and 50 epochs (γ 1e-3, 3 seeds) (Appendix B.7, stage 7).
6. Reducing epochs from 70 to 50 lowers the 3-seed mean A_π by 0.27 pp, less than X, while BA and Macro-F1 are slightly higher; training accuracy is already about 0.999 at 50 epochs.
7. At 50 epochs, after changing the monolithic model's wd from 1e-4 to 0.01, the 3-seed paired mean of monolithic model minus MoE changes from −0.46 pp to +0.74 pp (validation set). The direction of the comparison between the monolithic model and MoE depends on whether the monolithic model's wd is tuned. The monolithic model's wd was selected on these seeds, so this number is biased high; performance conclusions look only at the test set.
8. After changing σ0 from 0.2 to 0.4, the 3-seed paired mean of monolithic model (wd 0.01) minus MoE changes from +0.74 pp to +0.15 pp (validation set); this is likewise only a number from the selection process.
9. In seed 0 of σ 0.4, τ 0.25, lr 3e-3 and in seed 2 of σ 0.8, the weakest expert's top-1 share is below 5% for most of training or for the first half, while usage is normal. This is the same as item 3: neither the balance loss nor usage can see this phenomenon.
10. auxfree with γ 1e-4 collapses in mid-training on all 3 seeds (minimum weighted usage close to 0, with 29 ~ 43 epochs below 5%) and recovers later. The exclusion criterion looks only at the last 10 epochs and catches only 1 of them (stage 7).
11. At the calibrated baseline (λ0 1.5, σ0 0.4, τ0 0.5), fuzzy is lower than fixed in both rounds: round 1 3-seed paired mean −0.61 pp (standard deviation 0.51), round 2 −0.84 pp (standard deviation 0.10); in round 2 all 3 seeds are lower by 0.78 ~ 0.96 pp (validation set, stage 8). The moving average in round 2 reduced the jumps of λ, σ but did not narrow the gap; the cause has not been identified. The open-loop replay's prediction of τ disagrees with the closed-loop result on 1 seed. ### 12.5 Overall limitations

- Each stage fixes the earlier choices before choosing the next one; this is not a full factorial search; every choice is conditional on the earlier settings.
- Only one parameter is changed at a time, so interactions are not visible.
- The training-hyperparameter stages mainly use a single seed (seeds are added only when deviating from the default); X comes from the range of 3 samples; the standard error of the 3-seed paired mean (0.14 ~ 0.42 pp) is the same order of magnitude as X.
- The primary metric is the maximum over the whole training run, which is biased high and noisier; across different numbers of epochs, longer training has more chances to pick a value.
- X, aux warmup, router, augmentation, and learning rate were all determined at 70 epochs and not rechecked at 50 epochs. The range over 3 seeds at the 50-epoch center point is 0.36 pp, only reported; X stays 0.50 pp; computed with 0.36 pp, the epoch choice also does not change.
- The same validation set is used for all selections, so validation A_π carries selection bias and is used only for selection; fuzzy reads the validation set during training, so conclusions involving it look only at the test set.
- The validation set is small (5,810 images, 100 images each for 11 classes), so single comparisons fluctuate easily; the observed single-seed gap fluctuation of about 1 pp (stage 6) is consistent with this, but the separate contributions of training randomness and validation-set sampling have not been distinguished. The reason for not enlarging the validation set is in 1.2.
- The 3 runs used to measure X also serve as the reference for later paired comparisons.
- Tuning effort is not fully equal across methods (12.2).
- The seed changes both the training subset and the initialization.
- The lower bound of X, 0.3 pp, and the exclusion criterion of 5% are set by hand, with no basis in the literature.
- The MoE wd verdict is close to the threshold (+0.40 pp vs X 0.50 pp); the current training setting (50 epochs, wd 1e-4) has the lowest 3-seed mean among the three tested epoch × wd combinations, with the gap within X (stage 4.4). The monolithic model's wd confirmation was added after seeing the results.
- The two models use different wd. The 3-seed mean of MoE wd 0.05 (0.7027) is higher than that of the 1e-4 in use (0.6987), with the gap smaller than X. MoE is not readjusted because the monolithic model is higher.
- The verdict for σ 0.4 is only 0.08 pp above X and is sensitive to the value of X (stage 6). Only some of the choices in stages 2 ~ 5 were rechecked (stage 6b), and X was not remeasured at σ 0.4.
- The exclusion criterion looks only at the last 10 epochs and cannot see collapse in mid-training (γ 1e-4 in stage 7).

## Appendix C. Old implementation of auxfree

The old implementation added the bias to the softmax probabilities (scores = softmax(s/τ) + b), unlike DeepSeek-V3 (the bias is added to each expert's independent sigmoid affinity). In a 400-step short experiment on 2026-10-22 (old router, constant lr, λ = 0): at step 100, looking only at the probabilities, all samples chose the same pair of experts; the bias grew linearly, but the imbalance did not recover within 400 steps; for 70% ~ 80% of samples the top-2 was changed by the bias. Background and evidence are in `E1_Competitive_Loss.md` Section 11 (11.2, 11.8, 11.9, 11.10) and `Status_2026-11-09.md`. E2 finished at 2026-11-09 09:57, and the σ 0 endpoint was confirmed on 3 seeds (`E1_Competitive_Loss.md` 11.11); E2b / E3a followed automatically at 09:58.

**This section has two layers.** What can be decided now (based on existing data): the paper direction, the setup and verdict of the tension test E3a, the controller's input and output variables and universes, the direction of the rules, the comparison methods, the metrics and verdict rules of E3c / E3d, and the order. ### 13.1 Paper direction and the question this section must answer (the author's decision, 2026-11-09, route b)

The paper's claims change to: (i) under day-based splits and multiple seeds, the accuracy of the five methods ties; (ii) the functional specialization of an upsampled sparse MoE is determined by the routing noise σ during the assignment-formation period and by the competitiveness of the classification loss, the balance loss opposes it, and assignment statistics (NMI) cannot see this; (iii) a training-time fuzzy controller uses the functional specialization signal to manage the "specialization vs. balance" trade-off. (i) and (ii) already have evidence (the σ 0 endpoint of ii awaits E2). This section answers (iii): **whether the controller can do what fixed parameters and linear schedules cannot.** If it cannot, the paper writes only (i), (ii), and the controller is demoted to a tool.

Four settled design decisions (the author decided per the recommendations, 2026-11-09):
1. **First test the oracle loss as the source of tension** (E3a). When specialization is strong, the competitive loss pushes down the usage of the weakest expert (E1 11.9: oracle minimum usage 10.8%, other runs 14 ~ 18%); this is the first sign that the balancing effect of λ has an opponent.
2. **Use `val_expert_agree` as the specialization signal** (denoted A: the fraction of the validation set on which the predictions of the two selected experts agree; the training code already logs it every epoch, at zero overhead). High = experts converge, low = experts differentiate. It is monotonic with functional specialization: across 24 runs with dense evaluation, fixed σ 0 is 0.54, σ 0.1 is 0.61 ~ 0.67, σ 0.2 is 0.77, σ 0.4 is 0.83 ~ 0.86, σ 0.8 is 0.88 ~ 0.90, auxfree 0.61 ~ 0.67, oracle 0.48, fuzzy round 3 0.85, schedule 0.89. The dense disagreement rate (about 25 seconds per epoch) is computed only once at the end of training as a reference and is not a controller input. Note: under the `expert` loss the high agreement rate is by construction (0.92); this section does not use the `expert` loss. A low A early in training means the experts are immature, not that they are already specialized (E1 5.2: mixprob rises from 0.68 to 0.89); the rule design must be insensitive to this (13.3).
3. **Remove τ.** τ is not a knob for either accuracy (stage 6) or specialization (E1 11.8: τ 0.25 / 1.0). All methods fix τ at 0.5; fuzzy v3 outputs only λ and σ. The comment R3-C6 on Δτ on the paper thereby disappears.
4. **Remove T_fast and T_slow.** Reasons: (a) the measurements in stage 6 show that T_fast is dominated by validation-set noise (per-epoch std of A_π 1.28 pp, correlation of trend values between adjacent epochs 0.14 ~ 0.23), and T_slow correlates with T_fast at 0.8, adding little independent information; in the three rounds of stage 8, R3 / R9, which contain T_slow "decreasing", were almost never triggered. (b) T_slow needs 11 epochs of history, which is why the early mode exists, while specialization is decided in the formation period, so the controller must work from epoch 4. (c) The goal of the new controller is the trade-off between specialization and balance; the accuracy trend does not directly reflect either, while A is a direct specialization signal. (d) The decisive one: stage 6 showed that λ, σ, τ within the acceptable range each affect accuracy by less than 1 pp, so even if the controller sees accuracy drop it has no actuator that can pull accuracy back; a feedback input without an actuator only adds rules and calibration burden. Cost (to be written into the limitations): the controller is blind to accuracy; if specialization hurts accuracy in some state, it will not notice; with existing data (σ 0 ~ 0.8 accuracy ties) the risk is small but non-zero.

### 13.3 E3b: controller v3

**Inputs (settled):** B (balance score, universe and partitions carried over from `fuzzy_v2_r3.json`); A (agreement rate, universe [0.4, 1.0]). **[draft]** The partitions of A follow the measurements in 13.1 item 2: Specialized trap [0.4, 0.4, 0.55, 0.65], Mixed tri [0.58, 0.72, 0.86], Homogeneous trap [0.80, 0.90, 1.0, 1.0]. **Outputs (universes settled, breakpoints [draft]):** λ ∈ [0.5, 4.5] (partitions carried over); σ ∈ [0, 0.4] (based on E1 11.8: at σ ≥ 0.4 specialization disappears, σ 0.8 has no extra value, σ 0 accuracy is within X with no collapse): Low trap [0, 0, 0.05, 0.15], Medium tri [0.10, 0.20, 0.30], High trap [0.25, 0.35, 0.4, 0.4]. **Rules (direction settled, levels [draft]; B × A, 9 rules in total).** How to read: rows are balance states, columns are agreement rate (high = converged, low = already differentiated), and each cell is the level λ and σ take in that state. Three-sentence logic: (a) when balance is normal or perfect, σ is low, letting specialization form (the main finding of 11.8); (b) when imbalanced, λ is high and σ medium, and the noise spreads the assignment out again (the mechanism of 11.3); the imbalanced row does not differentiate σ by A, because early in training a low A means the experts are immature, and giving high noise for "already differentiated" at that point would add noise exactly in the formation period, conflicting with the intent (review item 7); (c) when balance is normal and the experts converge, λ is low, relaxing the balance pressure to let the experts differentiate; otherwise λ is medium.

| B \ A | Specialized (already differentiated) | Mixed | Homogeneous (converged) |
|---|---|---|---|
| Unstable | λ High, σ Medium | λ High, σ Medium | λ High, σ Medium |
| Normal | λ Medium, σ Low | λ Medium, σ Low | λ Low, σ Low |
| Perfect | λ Low, σ Low | λ Low, σ Low | λ Low, σ Low |

Explanation of A's actual role (review item 6): in the normal and perfect rows σ does not vary with A; A only changes λ in the normal row. Under the mix loss λ is a weak specialization knob (11.8: the masking loss of λ 0.5 vs. 4.5 differs by only 1.5 pp), so A's effect on the results will be very small; A has a substantive role only when λ becomes an opponent of specialization under oracle (E3a (ii) holds). **Not judged:** comparison with fuzzy round 3 of main-experiment A (different design, description only); validation accuracy (fuzzy reads the validation set).

### 13.8 Limitations of this section (to be written into the paper)

- The whole E3 was designed after seeing the σ and oracle results and is a test of a post-hoc hypothesis; the verdict rules were written before running, but the hypothesis itself comes from the same data (seeds 0 ~ 2, the same validation set).
- The controller inputs A, B come from the validation set; as in Section 1.2, accuracy conclusions involving fuzzy look only at the test set; d1 and usage have no test-set version (dense evaluation is done only on the validation set), so the verdicts on specialization and balance can only use the validation set, with a selection bias toward fuzzy (the test-subset recomputation of 13.6 can partly mitigate this).
- The controller no longer reads the accuracy trend (13.1 item 4) and is blind to accuracy changes.
- A's effect on the results depends on the loss: under mix it only changes λ in the normal state, a small effect (13.3); the paper's wording must match the actual effect.
- The noise scale of d1 under oracle has not been measured (13.4).
- Single dataset, single backbone, 5 experts, image-level top-2 routing; the absolute values of specialization strength cannot be extrapolated.
- Specialization has so far not bought accuracy or cheaper inference (E1 11.8 item 4); the paper must say so explicitly; "what specialization is good for" can only be answered by controllability, diversity (any-of-5) and E5 (if done).
- fuzzy v3 and schedule v3 have the same output universe, but the schedule's trajectory is one hand-specified trajectory, not an optimal schedule; "better than the schedule" holds only for this schedule, and this schedule differs from fuzzy in formation-period noise (the to-do of 13.3).

### 14.2 Models and consistency

TorchScript is exported on the board with `deploy/export_models.py` (`torch.jit.script`, no freeze); at export it is checked against the eager model on 8 random inputs and 32 real images: argmax all identical, max logits difference < 1e-3, otherwise writing is refused.

Board × model results that miss the threshold are void; first check versions and preprocessing, then remeasure. ### 14.3 Latency

- **Data:** `val.csv` 5,810 images (day-split validation set), not the 59,793-image test set: latency does not depend on image content or weights, and 5,810 images take about 30 minutes on the RPi 4B, which is enough; the paper's sentence "over the full test set" is changed to "over the 5,810-image validation list".
- **6 runs per board:** monolithic model, fixed, schedule, auxfree, fuzzy round 3 (top-2), fixed top-1. The four MoE top-2 latencies should agree within noise, reported as a check.
- **Recording:** per image `model_ms` (only `model(x)`) and `e2e_ms` (including image reading, preprocessing); report mean, median, p90, standard deviation; throughput = N / total loop time.
- **Numbers for paper Table IV:** keep the submitted version's definition, end-to-end time per image = total loop time / N (`e2e_ms_from_loop`), throughput = 1000 / that; the `model_ms` mean as a supplementary column. The MoE-to-monolithic latency ratio uses the same-board `model_ms` mean.
- **Power criterion (Raspberry Pi):** read `get_throttled` once before and once after measurement; if not 0 at the end (under-voltage, frequency cap, throttling or soft temperature limit occurred since boot), the result is `power.ok=false`, that run is void, check the power supply, then reboot and remeasure. If already not 0 at the start, the script warns first.

### 14.4 Energy

- **Raspberry Pi (discharge method, `deploy/power_rpi.py`):** power bank Intenso F10000 (cells 3.7 V / 10000 mAh / 37.0 Wh, 5 V output 3 A max), start fully charged, run inference continuously until power cuts off, heartbeat written to disk every 10 seconds (fsync). Energy per sample E = E_out / N (N is the cumulative number of images), average power P = E_out / T. E_out: the manufacturer gives no rated capacity at the 5 V output side (checked 2026-11-09 in the official datasheet `Power-Bank_F10000_F20000.pdf` and manual `f10000_bda_alle.pdf`, intenso.de), so 37.0 Wh × [0.70, 0.85] is reported as two bounds. The lower bound 0.70 comes from the official manual's original sentence "Please note that while charging a device with a powerbank, about 30 % of the total capacity is used up just through the charging process. This is due, for example, through the loss of power from circuit warmth and voltage conversion." (a generic statement for the whole product line, not a measurement of the F10000; the manual also says it starts blinking at 5% remaining, and whether this 5% is included in the 30% is not stated); the upper bound 0.85 is a common upper limit measured on similar 5 V boost power banks, not manufacturer data. That is, E_out 25.9 ~ 31.5 Wh. **The same-board energy ratio of two models = N_single / N_MoE, independent of the E_out assumption; this is the number the paper can safely state; absolute values carry about ±10% capacity uncertainty (the interval above), stated as is (R4-C5).** Each board measures the monolithic model and fixed top-2 2 times each (the repetition R2-C3 asks for), interleaved; report mean and range. Duration per run: RPi 4B monolithic measured 7.27 hours (2026-11-10 run1); the original estimate of 4 ~ 5 hours (based on about 6 W at full `stress` load from online sources) was too short, meaning the inference load draws less power than `stress`, or the power bank efficiency is above 0.85, or both; current data cannot separate these. ~~RPi 5 to be added after measurement.~~ RPi 5 monolithic measured 4.72 hours (Goji, 2026-11-11 run1, see 14.11); run2 5.08 hours (2026-11-12). Page cache is not dropped by default (`--drop-caches` off).
- **Two power banks (author decision 2026-11-10):** to shorten total time, each board uses one fixed power bank and the two boards are measured in parallel: RPi 4B uses the Intenso F10000 (monolithic run1 already used it), RPi 5 uses the Goji G6P10BK25 (UK and EU representative on the label is Currys; 10000 mAh, 37 Wh / 3.7 V, USB-C 5 V / 3 A, two ports share 15 W, only one port used). The two power banks are not mixed on the same board: the energy ratio N_single / N_MoE holds only within the same board and the same power bank; mixing would bring the capacity difference of the two power banks into the ratio. The Pi 5 command adds `--bank-name "Goji G6P10BK25" --bank-cell-wh 37.0`, and the power bank name is recorded in the log header. There is no manufacturer data on the Goji's 5 V output-side capacity (none on the body label, box, or manual; on 2026-11-10 an online search by model number found nothing, and the manual of the similar model G6P10BK21 and the Currys product page refused access), so the Pi 5's E_out reuses 37.0 Wh × [0.70, 0.85], but both bounds are generic assumptions, not Goji data (0.70 comes from the Intenso manual and has a basis only for the F10000). No power-meter calibration is done (author's choice 2026-11-10); if calibration is added later, only the absolute values are replaced, and the measurement steps stay the same. Before formal use, the Goji likewise first powers the Pi 5 for a 10-minute full-load pre-check (no under-voltage in dmesg, `throttled=0x0`).
- **Power criterion for discharge:** every heartbeat records `get_throttled` (Pi 5 also records input voltage). When the power bank is nearly empty its output voltage drops, and under-voltage at the end is a normal part of discharge; so the verdict uses the time of the first heartbeat that is not 0: within the last 5% of total duration it is valid; if it appears earlier, or is already not 0 at the start, the run is void and not counted in the mean and energy ratio (`summarize_device.py --tail-tol 0.05`). Before each board's formal discharge, run 10 minutes at full load powered by the power bank, and start only if dmesg shows no under-voltage. 2026-11-10 Pi 5 verified: powered by F10000 (fully charged), negotiated current 3000 mA, 4-thread MoE (fixed top-2) at full load for 10 minutes, 7328 forward passes in total, no under-voltage in dmesg, `throttled=0x0` (under the same conditions with the 4B official power supply 7261 passes, 0.9% difference). RPi 4B verified the same day: with the power supply (4B official 5.1 V / 3 A) and with F10000, the same 4-thread MoE at full load for 10 minutes gave 2498 and 2497 forward passes respectively, no under-voltage in dmesg for either, `throttled=0x0` (the 4B has no PD negotiation and no `max_current` node).
- **Jetson (`deploy/power_jetson.py`):** first 2 minutes of idle sampling, then 20 minutes of continuous inference, ~~read whole-board input power every 10 seconds (VDD_IN / POM_5V_IN from INA3221 sysfs, tegrastats if unreadable)~~ whole-board input power is taken from tegrastats VDD_IN (measured by the on-board INA3221; revised 2026-11-11, see the next two items). Report P_idle, P_load (mean, standard deviation, sample count), energy per sample = P_load × end-to-end time per image, and incremental energy (P_load − P_idle) × time as a supplement. Each board measures the monolithic model, fixed top-2, fixed top-1 once each (the power standard deviation within 20 minutes already gives the fluctuation).
- **Jetson power source (checked 2026-11-11):** the INA3221 hwmon driver of JetPack 5/6 only provides voltage `in*_input` and current `curr*_input`, no power files (neither board has `power*_input`); the script's original "sysfs first" step could not read anything, and the actual source was tegrastats. Orin Nano: power rails VDD_IN / VDD_CPU_GPU_CV / VDD_SOC; tegrastats as a normal user already outputs VDD_IN (about 2.95 W at idle). Xavier NX: a normal user cannot read the power rail names (Permission denied), and tegrastats outputs no power items, so the Xavier NX power measurement runs as root (`sudo bash -c '...'`). Only the current value of VDD_IN (whole-board input) is taken, i.e. X in tegrastats `X/Y` (Y is an average, with the window not defined in NVIDIA documentation); the power rails are not summed (VDD_CPU_GPU_CV, VDD_SOC are components of VDD_IN; the old AGX Orin script summed them, which double-counts). The INA3221 driver is configured by default with no averaging, and one conversion of each of the 3 channels takes about 6.6 ms, so each reading is approximately one instantaneous value (on-board setting not verified).
- **Jetson sampling method (revised 2026-11-11, approved by the author):** the original script synchronously ran `timeout 3 tegrastats` every 10 seconds inside the inference loop, pausing inference for about 3 seconds each time, with readings falling in the pause (P_load too low, close to idle) and e2e including the pause (about 40% too high); both terms of energy per sample were wrong. The Orin Nano power measurement run with the original script (2026-11-11) is void, and its results were deleted. Changed to: in both the idle and inference stages, `tegrastats --interval 1000 --logfile` runs in the background, with inference-stage logging starting only after warm-up; after each stage, mean, standard deviation, and sample count are computed over all VDD_IN readings; power is not read inside the inference loop. Interval 1 second (original protocol 10 seconds; 2 minutes of idle at a 10-second interval gives only 12 readings, P_idle is unstable, which directly affects incremental energy; NVIDIA forums advise reading power nodes no faster than 1 second). At start, if tegrastats cannot read VDD_IN, it exits; if a stage has fewer than 90% of the expected readings, the result is flagged `power_readings_short`. Raw tegrastats logs are saved as `power_<model>_tegrastats_{idle,load}.log`. **Overhead check:** if the e2e of a power run is more than 2% higher than the `e2e_ms_from_loop` of the same-board same-model latency measurement, the tegrastats overhead is considered non-negligible, and we stop to investigate (basis for 2%: the two Xavier NX top-1 latency measurements differ in e2e by 0.5%, see 14.10).
- Numbers from the two methods are not compared across platform families (the note under Table V of the submitted version is kept).

### 14.6 Order and time

Laptop: copy the 5 `best.pth` → `make_references.sh` (about 20 minutes) → `pack_for_boards.sh`. Per board: `setup_board.sh` (20 ~ 40 minutes, depending on network speed) → export 6 models (10 ~ 20 minutes) → latency 6 runs (RPi 4B about 3 hours, RPi 5 about 1.5 hours, Jetson 1 ~ 2 hours) → energy (Raspberry Pi 4 discharges about 2 days per board, about 3 ~ 4 days serially with one power bank; Jetson about 1.2 hours per board). None of this blocks or is blocked by batch C and E3.

### 14.7 Limitations

- The absolute energy of the discharge method carries the uncertainty of power bank capacity and conversion efficiency (the manufacturer only gives "about 30% loss", see 14.4); only ratios are reliable. The Goji G6P10BK25 used by the RPi 5 does not even have this manufacturer statement, and both bounds of its [0.70, 0.85] interval are generic assumptions; the two boards use different power banks, so absolute energy is not compared across boards (14.5 only compares models on the same board anyway). Absolute values would require calibrating with one discharge through a USB power meter with a cumulative Wh reading; not scheduled.
- Latency is measured on validation set images and has nothing to do with test set images (a content-independent quantity); checkpoint uses seed 3 only (a weight-independent quantity).
- Thermal throttling is only recorded for temperature, not controlled; boards use default power modes (except Xavier NX, which uses `MODE_15W_6CORE`, see 14.1), not representing each one's optimal configuration.
- The 5% end tolerance of the discharge criterion is an empirical value with no literature basis (accepted by the author 2026-11-10); loosening or tightening it changes which discharge runs are valid; the summary lists the first-anomaly time of each run, so it can be rechecked.
- The Pi 5 uses a 5.1 V / 3 A power supply rather than the official 5 V / 5 A; full-load verification shows no under-voltage, but this does not represent the Pi 5 configuration with the official power supply.
- The submitted version's Xavier NX CPU result (5.1 seconds/image, 2.4 W) is clearly abnormal, cause not found; if it reappears in this round of measurement, stop and check the thread count and power mode.
